# Замер: трейл срабатывает по mark-цене вместо last (регистрация 2026-10-30, ДО прогона)

Волна «найти вариант, который зарабатывает при реальном исполнении» (решение владельца
30.10). Направление этого замера — по какой цене срабатывает трейл. Выход, отступ и
издержки меряют другие замеры волны.

## 0. Отправная точка
Замер «реализм трейла» (docs/measurements/2026-10-30-trail-realism.md, master e767637):
* модель E1m — биржевой трейл по last-цене 1m, активация сразу после филла, как у e5;
* net за сделку по половинам: W1 −0.065, W2 −0.057, rot H1 −0.180, rot H2 −0.004;
* почти весь разрыв с журналом — выходы по трейлу: журнал завышает трейл-выход на
  +0.31…+0.43R.

**Гипотеза.** Mark-цена считается от индекса нескольких бирж и сглаживает фитили одной
биржи. Если трейл срабатывает по mark, преждевременных выходов по фитилю меньше, и средний
трейл-выход ближе к пику.

## 1. Вопрос
Даёт ли срабатывание трейла по mark-цене net за сделку > 0 на всех четырёх половинах?
Сравнение идёт против модели E на тех же сделках.

## 2. Исполнимость — проверено до прогона по документации и коду
* **BingX** (официальная документация, `BingX-API/api-ai-skills`,
  `skills/swap-trade/api-reference.md`, Place order):
  - `workingType` — «Trigger price source: `MARK_PRICE` (mark price, **default**),
    `CONTRACT_PRICE` (last trade price), or `INDEX_PRICE`»;
  - для трейла: `activationPrice` — «Used with TRAILING_STOP_MARKET or TRAILING_TP_SL
    orders, default as the latest price (supporting different workingType)»;
  - `price` — дистанция трейла для TRAILING_STOP_MARKET.
* **Наш executor** (`app/v2/bingx_executor.py`, только чтение):
  - трейл ставится через ccxt 4.5.64:
    `create_order(sym, "market", side, qty, None, params={"trailingAmount": dist, "hedged": True, "reduceOnly": True})`;
  - ccxt шлёт `type=TRAILING_STOP_MARKET`, `price=dist` и НЕ шлёт `workingType`. Значит, по
    документации действует умолчание BingX — **MARK_PRICE**;
  - аварийный стоп при входе уходит как вложенный `stopLoss`. Ccxt подставляет в него
    `workingType: MARK_PRICE` по умолчанию.
  - **Следствие:** по документации e5 уже сейчас и трейл, и аварийный стоп срабатывают по
    mark BingX, а не по last. Подтвердить это может только демо — поле `workingType` в
    листинге открытых ордеров. Пока не подтверждено, это утверждение по документации.
* **Bybit** (`/v5/position/trading-stop`): у `trailingStop` нет параметра «по какой цене
  срабатывать». `tpTriggerBy` и `slTriggerBy` относятся только к TP и SL; справка Bybit
  описывает трейл по last. Переходить executor на Bybit замер не предлагает.
* **Данные.** Исторической mark BingX нет. Её заменяет mark-цена Bybit 1m
  (`/v5/market/mark-price-kline`). Обе считаются от индекса, но формулы бирж различаются.
  Это ограничение замера.

## 4. Модели (вход, стоп, активация +1.5R, отступ 0.2R, потолок и издержки — как в E)
* **E — база.** Всё по last 1m, путь внутри минуты по цвету свечи. Это модель E1m color
  замера e767637.
* **MT — основная.**
  - Филл и активация +1.5R — по last: e5 активирует трейл по стриму last-цены Bybit.
  - После активации пик и срабатывание (пик − 0.2R) — по mark 1m, путь внутри минуты по
    цвету mark-свечи, между минутами mark close → mark open.
  - Аварийный стоп −1R — по last, выход по уровню, как в E.
  - Исполнение срабатывания трейла — по last той же минуты, берётся худшая цена:
    - срабатывание на переходе от прошлой минуты (mark open уже за уровнем) — худшая из
      уровня и last open;
    - срабатывание внутри минуты — худшая из уровня и last low (LONG) / last high (SHORT).
  - Минута активации: пик = max(уровень активации, mark close этой минуты). Срабатывание
    проверяется только по mark close, исполнение — худшая из уровня и last close.
  - Минута без mark-бара: трейл в ней не двигается и не срабатывает. Число таких минут
    после активации — в отчёте.
* **Границы — информация, в критерий не входят:**
  - **MT-opt** — то же, что MT, но исполнение ровно по уровню трейла. Так же исполняет E,
    сравнение «на равных».
  - **MB — оба стопа по mark**, как e5 по умолчанию на BingX (раздел 2). Аварийный стоп −1R
    тоже срабатывает по mark, исполнение по тому же правилу худшей цены.

## 5. Паритет до вердикта (не сошлось — стоп, не интерпретируем)
1. База `measure_trail_realism.base()`: числа паритета 5y и ротации, как в e767637
   (3168/+169.8, 877/+59.1, 1292/−72.3, 1440/+192.7).
2. E, пересчитанная на кэше m1: net за сделку по половинам −0.065 / −0.057 / −0.180 /
   −0.004, допуск ±0.001.
3. Данные mark против last в окнах сделок. В отчёте — доля минут с |mark close − last
   close| > 1% от цены. Больше 5% минут — флаг.
4. Покрытие mark ≥ 95% окна [филл; выход M1h + 1ч). Сделки ниже порога исключаются из
   парного множества у всех моделей. Доля исключённых — в отчёте, покрытие половины < 90% —
   флаг.

## 6. Метрики (по каждой половине, для E, MT, MT-opt, MB)
* n;
* gross и net за сделку;
* ΣR net;
* максимальная просадка кумулятивного net R по времени выхода;
* доля трейл-выходов;
* средний трейл-выход (gross R);
* Δnet за сделку против E.

## 7. Критерий (записан до прогона, параметров нет)
**MT — «кандидат»**, если выполнены оба условия:
* net за сделку > 0 на ВСЕХ четырёх половинах (W1, W2, rot H1, rot H2);
* Δnet за сделку (MT − E) ≥ +0.05 на КАЖДОЙ половине.

Иначе — **«не кандидат»**. После прогона ничего не меняется и не перебирается.

## 8. Что предлагается владельцу при каждом исходе (прод сам не меняется)
* **«Кандидат».**
  1. Проверка на демо: в трейл-ордере явно `workingType=MARK_PRICE`, в листинге открытых
     ордеров подтвердить, что поле принято.
  2. Затем проверка вперёд по версии исполнения, отдельным решением.
* **«Не кандидат».** Идею закрыть.
* **В обоих случаях.** Если MB заметно отличается от E, реалистичная модель e5 — MB, а не
  E. Числа замера e767637 тогда пересчитать по MB, и демо-сверку вести против неё.
